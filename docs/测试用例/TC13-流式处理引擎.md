# TC13 流式处理引擎

## 1. 用例信息

| 项目 | 内容 |
| --- | --- |
| 用例编号 | TC13 |
| 用例名称 | 流式处理引擎（轻量 Python 服务） |
| 验证目标 | 验证消息通道连续量测事件的注入、按时间窗口聚合、异常检测、批次日志与四引擎日志中心展示，确认不依赖 Kafka/Flink |
| 对应需求 | 技术研究"支持实时多维度数据处理的智能策略引擎"；3.1 新增第四引擎；桑基图流式数据接入与客户数据连接 |
| 优先级 | 高 |
| 执行角色 | 系统管理员 |
| 测试入口 | `/health`、四引擎日志中心 `http://localhost:5173/data-catalog/security-governance/risks/log-center`、首页实时运行情况 |

## 用户故事

> 作为系统管理员，我希望看到消息通道的连续量测事件被流式处理引擎持续消费、按窗口聚合并识别异常，且整个过程可复现、可查日志，而不是依赖外部大数据框架。

## 2. 验收范围

1. 引擎以 Python 后台服务运行（daemon 线程轮询），无 Kafka/Flink 依赖。
2. 事件源 `security_streaming_events` 持续增长（确定性注入 + seed 预置）。
3. 窗口聚合 `security_streaming_windows` 按 60 秒 × 区域 × 量测项生成统计。
4. 异常检测：质量码非 normal 的事件计入 anomaly_count，异常率 ≥5% 批次标记 warning。
5. 批次日志 `security_streaming_runs` 记录消费事件数/窗口数/异常数/耗时。
6. `/health` 返回 `streamingProcessing: ok`。
7. 四引擎日志中心展示流式批次；首页实时运行情况展示"流式处理"卡片。
8. 分层策略流转桑基图把"流式处理引擎"作为接入通道列（第二列）的一种接入方式，形成"流式处理引擎 → 流式量测窗口统计 → 防护层 → 聚合输出 → 客户应用"链路，且与客户数据源（配电云主站）和客户应用（智慧城市/全链路监控）连接。

## 3. 前置条件

- 已完成 TC01；seed → migrate 初始化；runtime 容器已重建（含 streaming 模块）。

## 4. 操作步骤

### 步骤 1：核对引擎健康状态

```bash
curl -s http://127.0.0.1:8090/health | python3 -m json.tool
```

预期：`services.streamingProcessing = "ok"`；`configuration` 计数正常。

### 步骤 2：核对配置中心

```bash
docker exec nocobase-8196-postgres-1 psql -U nocobase -d nocobase -c \
  "SELECT \"groupKey\", \"key\", value FROM \"jcConfigCenterItems\" \
   WHERE \"groupKey\"='streaming-engine'"
```

预期：`streaming_engine_config` 含 `enabled=true`、`windowSeconds=60`、`pollIntervalSeconds=10`、`demoInjectEnabled=true`、`anomalyThreshold=0.05`。

### 步骤 3：核对事件源与窗口聚合

```bash
docker exec nocobase-8196-postgres-1 psql -U nocobase -d nocobase -c \
  "SELECT (SELECT count(*) FROM security_streaming_events) AS events, \
          (SELECT count(*) FROM security_streaming_windows) AS windows, \
          (SELECT count(*) FROM security_streaming_runs) AS runs"

docker exec nocobase-8196-postgres-1 psql -U nocobase -d nocobase -c \
  "SELECT region_code, measure_type, count(*) AS windows, sum(event_count) AS events, \
          sum(anomaly_count) AS anomalies \
   FROM security_streaming_windows GROUP BY 1, 2 ORDER BY 1, 2"
```

预期：三表持续增长（间隔 10 秒后重新查询数值递增）；窗口按 REGION-A/B × 电压/电流/有功功率分布；REGION-B 存在异常统计（seed 确定性质量码设计）。

### 步骤 4：核对批次日志

```bash
docker exec nocobase-8196-postgres-1 psql -U nocobase -d nocobase -c \
  "SELECT run_code, status, processed_events, window_count, anomaly_count, duration_ms \
   FROM security_streaming_runs ORDER BY id DESC LIMIT 5"
```

预期：最近批次 `processed_events>0`、`window_count>0`，含异常批次状态为 `warning`。

### 步骤 5：四引擎日志中心

1. 打开 `http://localhost:5173/data-catalog/security-governance/risks/log-center`。
2. 预期：标题"四引擎日志中心"，引擎筛选含"流式处理引擎"。
3. 选择"流式处理引擎"，预期显示真实批次（"流式窗口处理（N 个窗口）"、消费事件数、注入数、异常占比、时段、耗时）。
4. 点击最新流式日志行，预期展开"窗口明细"表格（窗口/区域/量测项/事件数/异常数/合计/均值）。

### 步骤 6：首页实时运行情况

1. 打开首页，确认"实时运行情况"tab 包含"流式处理"卡片。
2. 预期：卡片显示窗口数、累计事件数、异常数，数值与数据库一致且随时间递增。

### 步骤 7：可复现性（可选）

重跑 seed → migrate 后重启 runtime，预期事件回到 600 条未消费状态，引擎重新按窗口消费，结果与首次一致（确定性注入基于序号，不依赖随机数）。

### 步骤 8：桑基图流式数据接入验证

1. 打开首页 → "实时运行监控" → "分层策略流转"。
2. 预期链路描述：`数据源 → 接入通道（含流式处理引擎）→ 数据资源 → 防护层 → 输出模式 → 数据应用`（保持六列，不因流式引擎增加列）。
3. 核对接入通道列：数据库直连 / 已有 API / E 文件通道 / 流式处理引擎 四类并列；配电云主站量测数据源 → 流式处理引擎 → "流式量测窗口统计"（虚拟资源）→ "l2 明细受控" → "聚合输出" → "智慧城市大脑应用 / 全链路监控应用"。
4. 点击"流式处理引擎"节点（接入通道列），预期明细面板显示"流式处理批次日志"（真实批次：消费事件数/窗口数/异常数/状态/耗时）。
5. 点击"流式量测窗口统计"节点，预期明细面板显示"流式窗口统计"（窗口开始/区域/量测项/事件数/异常数/合计/均值）。
6. 点击"消息服务通道 → 流式处理引擎"连线，预期显示流式批次明细。

### 步骤 9：客户数据连接核对

确认桑基图全链路同时包含客户资料四视角：

- 数据源：10 个（用采 2.0、调控云、配电云主站等客户源系统）。
- 数据资源：16 个客户对齐资源 + 流式量测窗口统计。
- 数据应用：21 个客户应用（含智慧城市大脑、全链路监控等）。
- 流式分支：配电云主站（客户消息通道）→ 流式处理引擎（接入通道列）→ 窗口统计 → 聚合输出 → 客户应用。

## 5. 通过标准

- 引擎健康、配置完整、事件/窗口/批次持续增长。
- 窗口聚合与异常统计正确（区域×量测项口径）。
- 四引擎日志中心与首页卡片显示真实数据。
- 日志中心流式日志可展开窗口明细，展示引擎每一轮处理的真实记录。
- 桑基图包含流式数据接入链路，且与客户数据源/资源/应用连接。
- 无 Kafka/Flink/Redis 等外部中间件依赖。
